# خطة النسخ والاستعادة الاحتياطية لقاعدة بيانات HRM

## 1. الغرض

إنشاء منظومة موثوقة للنسخ الاحتياطي اليدوي والتلقائي والاستعادة لقاعدة بيانات نظام HRM، مع دعم:

- النسخ اليومي والأسبوعي والشهري.
- تشغيل نسخة يدوية عند الطلب.
- قاعدة بيانات MySQL 8.4 باسم `hrmair`.
- الملفات الكبيرة بصيغة SQL مثل `14-09-2026.sql`.
- الضغط والتشفير والتحقق من سلامة النسخ.
- تخزين محلي وخارجي وفق قاعدة 3-2-1.
- اختبار استعادة دوري مستقل عن الاستعادة الإنتاجية.
- سياسة احتفاظ وحذف آمن.
- صلاحيات وسجل تدقيق وتنبيهات.

هذه الخطة لا تعتبر النسخة سليمة لمجرد نجاح أمر التصدير؛ النسخة لا تعتمد إلا بعد التحقق منها واختبار استعادتها.

## 2. المعطيات المعتمدة

| العنصر | القيمة |
|---|---|
| إطار العمل | Laravel 13 |
| PHP | 8.3 أو أحدث |
| قاعدة الإنتاج | MySQL 8.4 |
| اسم القاعدة | `hrmair` |
| محرك الجداول | InnoDB |
| الترميز | `utf8mb4` |
| نظام التشغيل المستهدف | Windows |
| أداة المثال | HeidiSQL |
| صيغة المثال | SQL نصي كبير |
| مصدر الجدولة | Laravel Scheduler + Windows Task Scheduler |

### ملاحظة حول ملف المثال

الملف `C:\Users\pc\Downloads\14-09-2026.sql` هو dump صادر من HeidiSQL ويحتوي على إنشاء قاعدة البيانات والجداول والبيانات والفهارس والعلاقات. يستخدم كمرجع واختبار، وليس كصيغة التشغيل الأساسية للنسخ التلقائي.

النسخ الجديدة يجب أن تستخدم أدوات MySQL الرسمية، خصوصًا `mysqldump`، مع الضغط والتشفير والتحقق. لا يجب استيراد الملف مباشرة فوق قاعدة إنتاج غير فارغة؛ لأن أوامر `CREATE TABLE IF NOT EXISTS` لا تحذف الجداول القديمة ولا تستبدلها.

## 3. الأهداف ومستويات الحماية

### 3.1 الأهداف الوظيفية

- إنشاء نسخة قاعدة بيانات كاملة يدويًا.
- إنشاء نسخة تلقائية في وقت محدد.
- إدارة الجدول من لوحة التحكم.
- حفظ معلومات كل عملية وحالتها وحجمها ونتيجتها.
- التحقق من checksum بعد الإنشاء وبعد الرفع.
- اختبار الاستعادة إلى قاعدة مؤقتة.
- تنفيذ الاستعادة الإنتاجية بإجراءات حماية متعددة.
- منع حذف آخر نسخة سليمة.
- إرسال تنبيه عند الفشل أو غياب نسخة حديثة.

### 3.2 الهدف التشغيلي المقترح

| المؤشر | الهدف الأولي |
|---|---|
| RPO | فقدان لا يتجاوز 24 ساعة للنسخ اليومية |
| RTO | يحدد بعد قياس حجم القاعدة وزمن الاستعادة |
| النسخ اليومية | 14 نسخة |
| النسخ الأسبوعية | 12 نسخة |
| النسخ الشهرية | 12 نسخة |
| اختبار الاستعادة | أسبوعي في بيئة مؤقتة |
| النسخة الخارجية | بعد كل نسخة محلية ناجحة |

لا يجوز اعتبار هذه الأهداف نهائية قبل قياس حجم قاعدة الإنتاج وزمن النسخ والاستعادة فعليًا.

## 4. النطاق

### داخل النطاق

- قاعدة بيانات `hrmair` كاملة.
- الجداول والبيانات والفهارس والمفاتيح الأجنبية.
- Triggers وEvents وStored Routines إن وجدت.
- إعدادات النسخ والاحتفاظ.
- واجهة الإدارة.
- أوامر Artisan.
- التخزين المحلي والخارجي.
- التشفير والضغط وSHA-256.
- الاستعادة الاختبارية والإنتاجية.
- سجل التدقيق والتنبيهات.

### خارج النطاق في الإصدار الأول

- Point-in-Time Recovery عبر binlog/WAL.
- النسخ التفاضلي أو التزايدي.
- تبديل قواعد البيانات عبر Proxy أو Load Balancer.
- نسخ أجهزة البصمة نفسها.
- مزامنة قاعدة البيانات بين مركزَي بيانات.

يمكن إضافة هذه الميزات بعد نجاح الإصدار الأول واختبار زمن الاستعادة.

## 9. إنشاء النسخة في MySQL

يستخدم النظام `mysqldump` الرسمي، وليس HeidiSQL، مع الخيارات التالية مبدئيًا:

```text
--single-transaction
--quick
--routines
--triggers
--events
--hex-blob
--set-gtid-purged=OFF
--default-character-set=utf8mb4
```

### سبب الخيارات

- `--single-transaction`: نسخة متسقة لجداول InnoDB دون إيقاف النظام.
- `--quick`: قراءة البيانات على دفعات وعدم تحميل الجدول كاملًا في الذاكرة.
- `--routines`: تضمين الإجراءات المخزنة.
- `--triggers`: تضمين Triggers.
- `--events`: تضمين MySQL Events.
- `--hex-blob`: حماية البيانات الثنائية مثل القوالب الحيوية والصور.
- `--set-gtid-purged=OFF`: تقليل مشاكل الاستعادة على خادم مختلف.
- `--default-character-set=utf8mb4`: الحفاظ على العربية والبيانات متعددة اللغات.

لا تمرر كلمة المرور في arguments الظاهرة في العمليات أو السجلات. تستخدم آلية credentials آمنة أو متغيرًا مؤقتًا محميًا حسب بيئة التشغيل.

## 11. التشفير والتخزين

### 11.1 التشفير

- تشفير النسخة قبل رفعها إلى التخزين الخارجي.
- استخدام AES-256-GCM أو آلية Laravel تشفير موثقة ومناسبة للملفات الكبيرة.
- حفظ المفتاح خارج المستودع وخارج مجلد النسخ.
- دعم تدوير المفاتيح مع حفظ رقم إصدار المفتاح في metadata.
- منع كتابة المفتاح في logs أو رسائل الخطأ.

### 11.2 قاعدة 3-2-1

1. النسخة الأصلية في قاعدة الإنتاج.
2. نسخة محلية سريعة على قرص منفصل أو مسار نسخ احتياطي.
3. نسخة خارجية على S3 أو SFTP أو خادم منفصل.

يفضل تفعيل versioning وObject Lock أو WORM في التخزين الخارجي إن كانت الخدمة تدعم ذلك.

## 12. الجدولة

### الإعداد الافتراضي

```text
نسخة كاملة يومية: 02:00
نسخة أسبوعية: الأحد 03:00
نسخة شهرية: أول يوم من الشهر 04:00
اختبار استعادة: الأحد 06:00 على قاعدة مؤقتة
تنظيف الاحتفاظ: بعد نجاح النسخ والتحقق
```

تضاف الجدولة إلى Service Provider للوحدة، مع:

- `withoutOverlapping()`.
- `onOneServer()` إذا كان هناك أكثر من خادم.
- مهلة تنفيذ مناسبة.
- عدم تشغيل عمليتي نسخ لنفس قاعدة البيانات في الوقت نفسه.
- تسجيل `starting` و`finished` و`failed`.

على Windows يجب إنشاء مهمة في Windows Task Scheduler لتشغيل:

```text
php artisan schedule:run
```

كل دقيقة، مع استمرار عامل الطوابير.

## 14. الاستعادة الاختبارية

تنفذ الاستعادة الاختبارية على قاعدة منفصلة مثل:

```text
hrmair_restore_test_20260914_020000
```

التسلسل:

1. اختيار آخر نسخة `verified`.
2. التحقق من SHA-256.
3. فك التشفير.
4. فك الضغط.
5. إنشاء قاعدة اختبار جديدة.
6. استيراد dump إليها.
7. تشغيل فحوصات الجداول والعلاقات.
8. تنفيذ استعلامات صحة أساسية.
9. التحقق من وجود البيانات العربية والبيانات الثنائية.
10. قياس زمن الاستعادة.
11. حذف قاعدة الاختبار بعد التسجيل.
12. إرسال النتيجة.

لا تعتبر النسخة موثوقة تشغيليًا إذا فشلت في اختبار الاستعادة.

## 15. الاستعادة الإنتاجية

لا تستورد ملف SQL مباشرة فوق قاعدة الإنتاج دون حماية. الإجراء الإلزامي:

1. التحقق من صلاحية المستخدم.
2. طلب سبب الاستعادة.
3. طلب تأكيد صريح.
4. التحقق من checksum والنسخة.
5. إنشاء نسخة طوارئ من قاعدة الإنتاج الحالية.
6. اختبار النسخة المراد استعادتها على قاعدة مؤقتة.
7. إيقاف المهام التي تكتب إلى قاعدة البيانات.
8. إيقاف استقبال العمليات الحساسة أو وضع النظام في الصيانة.
9. تنفيذ الاستعادة.
10. تشغيل `backup:health-check`.
11. فحص تسجيل الدخول والبيانات الأساسية.
12. إعادة تشغيل الطوابير والجدولة.
13. إزالة وضع الصيانة.
14. تسجيل النتيجة.
15. إرسال تقرير للمسؤولين.

عند الفشل، لا تحذف نسخة ما قبل الاستعادة، ويجب محاولة الرجوع إليها وفق إجراء Rollback واضح.


- إشعار داخل النظام.
- البريد الإلكتروني.
- Webhook أو Telegram عند توفره.
- Log مخصص للنسخ.

## 21. التعامل مع ملفات التطبيق

إذا كان النظام يعتمد على صور الموظفين أو صور الوجوه أو المرفقات، فنسخ قاعدة البيانات وحدها لا يكفي. يجب توفير نسخة منفصلة للمجلدات المطلوبة، مثل:

```text
storage/app/
storage/app/public/
```

مع استثناء:

```text
node_modules/
.git/
cache/
temporary files
development artifacts
```

تحدد قائمة الملفات رسميًا قبل التنفيذ. لا تحفظ `.env` ضمن نسخة عادية قابلة للتنزيل؛ تحفظ أسرار الإنتاج في Secret Manager أو مخزن محمي.

## 24. إجراءات التشغيل اليومية

### عند نجاح النسخ

1. التحقق من حالة `completed`.
2. التأكد من `verification_status=verified`.
3. التأكد من وجود النسخة الخارجية.
4. مراجعة الحجم مقارنة بالأيام السابقة.
5. مراجعة مساحة التخزين.

### عند فشل النسخ

1. قراءة `error_code` و`error_message`.
2. التحقق من مساحة القرص.
3. التحقق من اتصال MySQL.
4. التحقق من وجود `mysqldump.exe`.
5. إعادة التشغيل يدويًا بعد معالجة السبب.
6. التأكد من وصول تنبيه للمسؤول.
7. عدم اعتبار النسخة السابقة بديلًا دائمًا دون تسجيل الحادثة.

### عند طلب استعادة

1. تحديد سبب الاستعادة.
2. اختيار نسخة `verified`.
3. اختبارها أولًا.
4. إنشاء نسخة من الإنتاج الحالي.
5. أخذ موافقة المسؤول.
6. تنفيذ الاستعادة في وقت مناسب.
7. تشغيل فحوصات الصحة.
8. توثيق النتيجة.

## 27. ملاحظات مهمة

- لا يوجد نظام يضمن فقدانًا صفريًا أو توافرًا بنسبة 100% دون بنية تكرار ومراقبة واختبارات مستمرة.
- وجود ملف SQL لا يعني أنه قابل للاستعادة.
- نجاح `mysqldump` لا يكفي وحده لاعتماد النسخة.
- لا يتم الاعتماد على التخزين المحلي وحده.
- لا يتم استيراد ملف HeidiSQL مباشرة فوق قاعدة إنتاج غير فارغة.
- لا تحفظ كلمات مرور قاعدة البيانات أو مفاتيح التشفير داخل Git أو logs.
- لا تبدأ الاستعادة الإنتاجية قبل اختبار النسخة على قاعدة مؤقتة.
- يتم تنفيذ `php artisan migrate` فقط وفق قرار توافق مدروس، وليس تلقائيًا بعد كل استعادة.
