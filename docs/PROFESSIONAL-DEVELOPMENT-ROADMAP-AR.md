# خطة التطوير الاحترافي الآمن لمشروع HRM

**تاريخ إعداد الخطة:** 2026-09-14  
**نطاق الخطة:** الأمور الحرجة، المظهر العام، UI/UX، السرعة والاستقرار  
**قاعدة غير قابلة للتفاوض:** لا يتم تغيير وظيفة قائمة أو مكوّن قائم إلا بعد وجود اختبار حماية، وقياس قبل/بعد، وخطة رجوع واضحة.

## 1. الملخص التنفيذي

المشروع نظام HRM فعلي مبني على Laravel 13 وPHP 8.3 وVue 3 وInertia وTailwind، ويضم وظائف حساسة جداً: الحضور والانصراف، حساب الغياب، المناوبات والدوريات، التكامل مع أجهزة البصمة، مزامنة القوالب، الصلاحيات، التقارير، والإجازات.

أظهر الفحص أن المشروع ليس في مرحلة تأسيس؛ توجد بنية واختبارات ومواصفات وتحسينات سابقة جيدة. لذلك فإن المسار الصحيح ليس إعادة كتابة النظام، ولا تبديل إطار العمل، ولا تغيير قاعدة البيانات بشكل شامل. المسار الآمن هو **تحسين تدريجي محافظ على السلوك**:

1. تثبيت خط أساس تشغيلي ووظيفي قابل للمقارنة.
2. حماية المسارات الحرجة باختبارات تكامل ومقارنات مخرجات.
3. تحسين الأداء من خلال القياس، الفهارس، eager loading، التجميع، والكاش الآمن.
4. توحيد الواجهة فوق المكونات الحالية بدلاً من بناء واجهة موازية.
5. تحسين تجربة الاستخدام والوصول وRTL تدريجياً.
6. إدخال مراقبة واسترجاع سريع قبل التوسع في أي تعديل.

## 2. نتائج الفحص الفعلية

### 2.1 خط أساس المشروع

| المجال | النتيجة المرصودة |
|---|---|
| الإطار | Laravel 13.19، PHP 8.3.28 |
| الواجهة | Vue 3.5، Inertia 3، Vite 8، Tailwind 4 |
| الوحدات | 16 وحدة موجودة فعلياً في مجلد `Modules` |
| وحدات المسارات | 31 ملف routes بين web/api/channels |
| Controllers | 54 Controller داخل الوحدات |
| Services | 70 Service داخل الوحدات |
| صفحات Vue | 151 صفحة |
| مكونات Vue | 54 مكوناً تقريباً داخل `resources/js/Components` |
| ملفات الاختبار | 67 ملف اختبار بين Unit وFeature |
| قاعدة البيانات الحالية | MySQL في بيئة التشغيل المرصودة، SQLite معزول للاختبارات |
| Queue | database في بيئة التشغيل المرصودة |
| Cache/Session | file في بيئة التشغيل المرصودة |
| Debug | معطل في البيئة المرصودة |
| RTL/اللغة | العربية وRTL هما الوضع الأساسي |
| نظام التصميم | Mistral-inspired مع بوابة `npm run lint:tokens` |

### 2.2 نقاط القوة الحالية

- توجد مواصفة دستورية واضحة تلزم بتدفق `Controller → Service → Repository → Model`.
- توجد اختبارات مركزة على أكثر الأجزاء حساسية: الحضور، التقارير، أجهزة البصمة، المزامنة، الصلاحيات، والدوريات.
- توجد حماية صريحة تمنع تشغيل الاختبارات على قاعدة بيانات حقيقية داخل `tests/TestCase.php`.
- توجد تحسينات موثقة سابقة لـ N+1، الفهارس، دقة التقارير، الصلاحيات، تدوير السجلات، واستقرار التشغيل الطويل.
- توجد مكونات UI مشتركة كثيرة: `DataTable`, `FormInput`, `FormSelect`, `FormModal`, `Button`, `Card`, `Pagination` وغيرها.
- بوابة التصميم الحالية ناجحة وقت الفحص: الألوان الخام، aria-label العربي الصلب، وradius خارج النظام لم تنتج مخالفات.
- ملف `specs/012-ui-ux-improvement/PROGRESS.md` يوثق إنجاز مراحل كبيرة في التوحيد البصري وRTL وإمكانية الوصول.

### 2.3 نقاط الخطر والأولوية

#### أ. الوظائف الحساسة

- `Attendance` و`AttendanceIntegration` و`FingerprintDevices` مترابطة، وأي تغيير غير معزول قد يغيّر تسجيل الحضور أو ترتيب المزامنة.
- قواعد الغياب والتقارير تتعامل مع الورديات الليلية، النوافذ الزمنية، أيام الراحة، الإجازات، الجلسات المفتوحة، والتوقيت المحلي؛ لا يجوز تبسيطها أو نقلها دون اختبارات سيناريوهات كاملة.
- مزامنة الأجهزة تتضمن أوامر، إعادة محاولات، منع تكرار، kill switches، ومراحل تسليم ADMS؛ التغيير فيها يجب أن يكون additive وقابلاً للإيقاف.
- `config` وroutes ليست cached حالياً حسب `php artisan about`؛ هذا يؤثر في سرعة الإقلاع والطلبات ويجب تحسينه في مرحلة تشغيلية مستقلة بعد التحقق من قابلية cache.

#### ب. الأداء

- توجد مواصفات وتحسينات سابقة للأداء، لكن يلزم إنشاء قياسات مستمرة موحدة بدلاً من الاعتماد على قياسات متفرقة.
- توجد جداول وواجهات تستخدم `<table>` مباشرة في صفحات حرجة مثل Dashboard وتقارير الحضور وFace Sync؛ لا ينبغي تحويلها آلياً إلى `DataTable` إذا كانت جداول تقارير خاصة، لكن يجب تقييمها وتوحيدها أو إنشاء مكون متخصص يحافظ على الوظائف.
- يوجد استيراد كامل لـ Font Awesome في `resources/js/app.js`، وهو مرشح واضح لتقليل حجم الحزمة، لكن يجب قياس تأثيره قبل التغيير والتأكد من عدم كسر الأيقونات الديناميكية.
- يوجد listener مباشر لـ `resize` في `AppLayout.vue`؛ يستحسن ضبطه بـ throttle أو `matchMedia` بعد اختبار سلوك فتح/طي القائمة على الهاتف.
- إعدادات الإنتاج الفعلية تختلف عن `.env.example` في بعض drivers؛ يجب توثيق ذلك وفحص cache/queue/session قبل أي تغيير.

#### ج. UI/UX

- النظام لديه أساس تصميم موحد قوي، لكن بعض الصفحات ما زالت تحتوي جداول وحقول HTML مباشرة، خصوصاً التقارير ولوحات الأجهزة.
- توجد حاجة إلى توحيد تدفقات التحميل، حالات الفراغ، الأخطاء، التأكيد، الرسائل، والفلاتر على مستوى جميع الصفحات.
- يجب الحفاظ على RTL وLTR واللغة العربية والإنجليزية في كل تحسين، وعدم اعتبار نجاح العرض بالعربية كافياً.
- لا يجب إدخال الوضع الليلي في هذه الخطة الحرجة قبل اكتمال الأساس؛ هو تغيير واسع بصرياً وليس أولوية تشغيلية.

#### د. حالة المستودع أثناء الفحص

وجدت تعديلات محلية قائمة قبل إعداد هذه الخطة في:

- `Modules/AttendanceIntegration/app/Services/BiodataIngestionService.php`
- `Modules/FingerprintDevices/app/Services/FingerprintTemplateDistributionService.php`
- `tests/Unit/Modules/AttendanceIntegration/BiodataIngestionServiceTest.php`
- `tests/Unit/Modules/FingerprintDevices/FingerprintTemplateDistributionServiceTest.php`

لم يتم تعديل هذه الملفات أو عكسها. يجب اعتبارها تغييرات قائمة تحتاج مراجعة مستقلة قبل دمج أي مرحلة تمس نفس المسارات.

## 3. قواعد العمل الآمن

### 3.1 ممنوعات صريحة

- ممنوع إعادة كتابة وحدات الحضور أو الأجهزة دفعة واحدة.
- ممنوع تغيير أسماء routes أو payloads أو أعمدة قاعدة البيانات القديمة دون طبقة توافق واختبارات.
- ممنوع حذف جدول أو فهرس أو migration قائمة بلا migration عكسية ودليل استخدام قبل/بعد.
- ممنوع نقل منطق من Service إلى Controller أو إدخال استعلامات مباشرة في Controller.
- ممنوع تحويل عمليات ثقيلة إلى Queue دون idempotency، retries، failed-job handling، ومراقبة.
- ممنوع تحويل كل الجداول إلى مكون واحد إذا كان ذلك يغير الفرز، التصدير، الأعمدة، أو اختصارات لوحة المفاتيح.
- ممنوع تغيير إعدادات الإنتاج أثناء التشغيل الحي دون نافذة صيانة أو rollout تدريجي.

### 3.2 بوابة كل تغيير

لا ينتقل أي تغيير إلى البيئة التالية إلا بعد:

1. `php artisan test` أو مجموعة الاختبارات المتأثرة.
2. `php artisan pint --test` أو تشغيل Pint وفق سياسة المشروع.
3. `npm run lint:tokens` لأي تغيير UI.
4. `npm run build` لأي تغيير JavaScript/CSS/Vue.
5. اختبار route وpermission للمسارات المتأثرة.
6. مقارنة عدد الاستعلامات وزمن الاستجابة عند تغييرات الأداء.
7. حفظ دليل قبل/بعد في `docs/evidence` أو مجلد مواصفة المرحلة.
8. وجود rollback عملي ومجرب.

## 5. خطة التنفيذ المرحلية

## المرحلة 0: خط أساس وحماية قبل التعديل

**الهدف:** معرفة الحالة الحالية وإمكانية إثبات عدم الكسر.

### الأعمال

- حفظ نسخة من `php artisan route:list --json` و`php artisan about` في دليل المرحلة.
- تشغيل الاختبارات كاملة مع تسجيل عدد الاختبارات والزمن والإخفاقات.
- تصنيف المسارات إلى: مصادقة، CRUD، تقارير، حضور، أجهزة، ADMS، API، بث حي.
- تسجيل أهم سيناريوهات الأعمال كاختبارات حماية، وليس فقط اختبارات شكلية:
  - تسجيل punch جديد.
  - punch مكرر.
  - مستخدم غير معروف من الجهاز.
  - biodata للوجه والبصمة.
  - جهاز غير متصل ثم عودة الاتصال.
  - إعادة محاولة الأمر وفشل الحد الأقصى.
  - وردية ليلية وجلسة مفتوحة.
  - عطلة ويوم راحة وإجازة.
  - تقرير يومي/شهري/DOCX بنفس النتيجة.
  - منع مستخدم بلا permission.
- إنشاء baseline للأداء لصفحات Dashboard، Users، Attendance Reports، Live Attendance، Face Sync.
- حفظ أحجام ملفات build الحالية ووقت build.

### معيار الإنجاز

- كل سيناريو حرج له اختبار آلي أو checklist تشغيلية موثقة.
- لا توجد اختبارات حمراء غير مصنفة.
- توجد أرقام قبل/بعد للاستعلامات والزمن وحجم الحزمة.

## المرحلة 1: تثبيت الوظائف الحرجة

**الهدف:** تقليل احتمال كسر الوظائف قبل تحسينها.

### 1.1 الحضور والتقارير

- تثبيت عقود `PunchIngestionService`, `SchedulePunchClassifierService`, `DailyReportService`, `MonthlyReportService`, `AbsenceCalculationService` باختبارات سيناريوهات.
- إضافة اختبارات property-like للحدود الزمنية: قبل النافذة، داخلها، بعدها، منتصف الليل، واليوم التالي.
- إضافة اختبارات مقارنة بين التقارير اليومية والشهرية والتصدير.
- منع أي refactor داخلي من تغيير ترتيب النتائج أو الحالات أو الأرقام دون قرار موثق.

### 1.2 الأجهزة والمزامنة

- تثبيت عقد ADMS وdevice push وbiodata وdevice commands باختبارات HTTP وdatabase.
- توثيق states المسموحة للأمر: pending, sending, completed, failed, held أو ما يقابلها فعلياً.
- التأكد من idempotency لكل عملية توزيع fingerprint/face/user.
- إبقاء kill switch واختبارات anti-flood جزءاً من بوابة النشر.
- إضافة مراقبة للصفوف الفاشلة وإعادة المحاولة، دون تغيير القيم الحالية أولاً.

### 1.3 الصلاحيات والمسارات

- حصر كل route عام ومحمٍ وصلاحية مرتبطة به.
- إضافة اختبار آلي لكل مسار حرج يثبت: guest redirect، forbidden، authorized success.
- عدم حذف أو إعادة تسمية permission قائمة؛ أي permission جديدة تكون additive.
- مراجعة route cache بعد إثبات أن جميع bindings وmodule routes تسجل بشكل صحيح.

## المرحلة 2: تحسين الأداء من دون تغيير السلوك

**الهدف:** تخفيض الزمن والاستعلامات مع تطابق المخرجات.

### 2.1 منهج القياس

- تسجيل query count وquery time لكل endpoint حرج في بيئة اختبار بيانات مماثلة للإنتاج.
- تفعيل slow-query logging بحد 100ms في بيئة قياس أو sampling، مع منع تسجيل الأسرار والبيانات الحيوية.
- قياس p50 وp95 وp99 للصفحات والـ endpoints بدلاً من متوسط واحد.
- قياس استهلاك الذاكرة للـ queue jobs والتقارير.

### 2.2 Backend

- فحص N+1 في كل report/list endpoint، مع `with()` أو `load()` فقط عند إثبات الحاجة.
- تحديد الأعمدة المطلوبة بدلاً من `select *` في القوائم الكبيرة.
- استخدام pagination وcursor/chunk للعمليات واسعة النطاق.
- مراجعة الفهارس المركبة بناء على `EXPLAIN` الفعلي، لا على التخمين.
- عدم حذف فهرس إلا بعد إثبات أن الاستعلامات البديلة تستخدم فهارس مناسبة وأن migration rollback مجرب.
- استخدام cache للبيانات الثابتة أو شبه الثابتة فقط: settings، permissions، شجرة الشركات/الفروع، إحصاءات قصيرة العمر.
- وضع invalidation صريح لكل cache key عند create/update/delete.
- نقل التصدير والتقارير الثقيلة والمزامنة إلى Queue فقط إذا كانت العملية قابلة لإعادة التنفيذ وآمنة من التكرار.
- فصل queues حسب طبيعة العمل وعدم تغيير timeout/retry قبل مطابقة worker timeout مع job timeout.

### 2.3 Frontend

- تقسيم المكونات الثقيلة مثل charts وواجهات المراقبة إلى async chunks.
- قياس أثر Font Awesome ثم استبدال الاستيراد الكامل باستيراد انتقائي إن أمكن دون كسر الأيقونات الديناميكية.
- مراجعة `import.meta.glob` وتقسيم صفحات Inertia إذا كان build ينتج chunk كبيراً.
- منع جلب البيانات المكرر بين props وطلبات إضافية.
- تطبيق debounce للبحث وthrottle للأحداث المتكررة.
- استخدام `computed` للقيم المشتقة وتجنب watchers التي تعيد طلب نفس البيانات.
- إضافة loading skeleton وpartial reload حيث لا يتطلب الأمر إعادة الصفحة كلها.

### معيار الإنجاز

- نفس المخرجات الوظيفية قبل/بعد.
- انخفاض مثبت في query count أو p95 أو حجم الحزمة.
- عدم زيادة استهلاك الذاكرة أو failed jobs.
- دليل `EXPLAIN` وbenchmark محفوظ لكل تحسين.

## المرحلة 3: توحيد UI/UX للصفحات الحرجة

**الهدف:** جعل الواجهة متناسقة وقابلة للاستخدام دون إعادة تصميم شاملة خطرة.

### 3.1 ترتيب الصفحات

1. Dashboard.
2. الحضور المباشر والتقارير اليومية/الشهرية.
3. Users وCompanies وBranches.
4. Fingerprint Devices وFace Sync وLive Scan.
5. Shifts/Rotations والجداول.
6. Vacations والصلاحيات والإعدادات.

### 3.2 قواعد التنفيذ

- استخدام `PageHeader`, `Card`, `Button`, `FormInput`, `FormSelect`, `FormDatepicker`, `FormModal`, `ConfirmDialog`, `Alert`, `EmptyState`, `LoadingSpinner`, `Pagination` حيث ينطبق.
- عدم تحويل جدول تقرير خاص إلى `DataTable` بشكل آلي إذا كان يحتاج أعمدة مركبة أو خلايا محسوبة؛ بدلاً من ذلك إنشاء مكون جدول تقرير مشترك يحافظ على نفس المخرجات.
- توحيد ترتيب الصفحة: عنوان، وصف مختصر، إجراءات، فلاتر، محتوى، pagination، حالة فارغة.
- توحيد الرسائل بعد الحفظ والحذف والفشل مع `Alert` ورسائل ترجمة.
- توحيد حالات loading وdisabled وretry وعدم ترك زر بلا feedback.
- توحيد نمط confirmation للأفعال المدمرة، خصوصاً أوامر الأجهزة.
- دعم RTL وLTR بخصائص منطقية `start/end/ms/me/ps/pe`.
- الحفاظ على ألوان `mistral-*` وعدم إدخال ألوان Tailwind خام.
- الحفاظ على `SunsetStripeBand` وارتفاعه المحكوم 3px.

### 3.3 الوصول Accessibility

- مراجعة focus order في كل modal وdropdown وtable.
- التحقق من keyboard navigation للبحث، الفلاتر، الفرز، التبويبات، والقوائم.
- إضافة labels وdescriptions للحقول الحساسة، خصوصاً device credentials وface/fingerprint actions.
- استخدام `aria-live` فقط للرسائل التي يحتاجها المستخدم، وعدم إغراق قارئ الشاشة بتحديثات realtime.
- اختبار contrast للـ semantic states في العربية والإنجليزية.

## المرحلة 4: تحسين التنقل وتجربة التشغيل اليومية

**الهدف:** تقليل الوقت الذهني والعملي للموظف دون تغيير الصلاحيات أو workflows.

### الأعمال

- ترتيب القائمة حسب المهام اليومية لا حسب البنية الداخلية فقط، مع إبقاء أسماء routes كما هي.
- تحسين Command Palette والبحث السريع مع احترام permissions.
- حفظ الفلاتر الأخيرة محلياً فقط عندما لا تحتوي بيانات حساسة.
- توفير روابط واضحة من Dashboard إلى الحالات التي تحتاج إجراء.
- تحسين رسائل الأخطاء لتوضح الإجراء التالي، دون كشف stack trace أو بيانات داخلية.
- إظهار حالة مزامنة الأجهزة بطريقة مفهومة: آخر اتصال، pending، failed، retry.
- تحسين تجربة التقارير: نطاق التاريخ، الفلاتر، التصدير، حالة المعالجة، والتنبيه عند تقرير كبير.

## المرحلة 5: التشغيل والمراقبة والإطلاق الآمن

**الهدف:** جعل التحسينات قابلة للمراقبة والرجوع في بيئة التشغيل الطويل.

### الأعمال

- توثيق إعدادات production الفعلية منفصلة عن `.env.example` دون نشر secrets.
- تفعيل config/routes/events/views cache في نافذة اختبار ثم الإنتاج بعد التحقق من module discovery.
- إضافة health checks لـ database، queue، cache، Reverb/البث، وbridge الأجهزة.
- مراقبة failed jobs، queue lag، slow requests، slow queries، log size، وdisk usage.
- تحديد retention للسجلات والملفات المؤقتة وdebug snapshots مع عدم حذف أدلة مطلوبة للتحقيق.
- وضع runbook للإقلاع، التوقف، إعادة worker، rollback migration، وتعطيل مزامنة الأجهزة مؤقتاً.
- نشر تدريجي: staging أو مستخدمين داخليين، ثم نسبة محدودة، ثم كامل النظام.
- لا يتم rollout لتغيير device sync أو attendance calculation في وقت ذروة الحضور.

## 6. مصفوفة المخاطر والضوابط

| الخطر | الاحتمال | الأثر | الضابط |
|---|---:|---:|---|
| تغيير حساب الغياب أو التقرير | متوسط | حرج | اختبارات مقارنة يومية/شهرية/DOCX + rollout مؤجل |
| تكرار أو فقد أمر جهاز | متوسط | حرج | idempotency + anti-flood + audit + kill switch |
| كسر permission أو route | متوسط | عالٍ | route/permission matrix + Feature tests |
| N+1 بعد تحسين UI | متوسط | متوسط | query budget وbenchmark لكل صفحة |
| كسر RTL/LTR | متوسط | متوسط | اختبار بصري على اللغتين واتجاهي العرض |
| تضخم JavaScript | متوسط | متوسط | build size budget وbundle report |
| امتلاء logs أو failed jobs | متوسط | عالٍ | retention + alerts + runbook |
| cache stale بعد تعديل البيانات | متوسط | عالٍ | invalidation اختبارية ومفاتيح namespaced |
| migration غير قابلة للرجوع | منخفض | حرج | backup/rollback/EXPLAIN ونافذة صيانة |

## 7. معايير الجودة المقترحة

هذه أهداف قياس وليست أرقاماً يجب فرضها قبل معرفة baseline:

- لا regression في اختبارات الوظائف الحالية.
- 100% من المسارات الحرجة مغطاة باختبار وصول وصلاحية.
- 100% من تغييرات الحضور والأجهزة لها اختبار idempotency أو مقارنة مخرجات.
- p95 للصفحات الحرجة لا يزيد عن baseline، والهدف تخفيضه تدريجياً 20% بعد القياس.
- لا endpoint حرج يسبب N+1 واضحاً في بيانات مماثلة للإنتاج.
- build JavaScript لا يزيد عن baseline، والهدف خفضه بعد تحليل bundle.
- لا failed jobs جديدة غير مصنفة خلال 24 ساعة من rollout.
- لا أخطاء console أو Vue غير متوقعة في الصفحات الحرجة.
- بوابة `npm run lint:tokens` ناجحة دائماً بعد تغييرات UI.
- جميع الصفحات الحرجة تعمل بالعربية/RTL والإنجليزية/LTR.

## 8. استراتيجية الاختبار

### قبل كل مرحلة

- Unit tests للخدمات المتأثرة.
- Feature tests للـ controllers/routes/permissions.
- Integration tests للتكامل مع الأجهزة عند المساس به.
- اختبار migration على نسخة بيانات غير إنتاجية.
- اختبار build وtoken lint لتغييرات الواجهة.

### بعد كل مرحلة

- تشغيل suite كاملة في بيئة معزولة.
- مقارنة snapshots أو JSON للنتائج الحساسة.
- فحص route list وpermissions.
- مراجعة logs وfailed jobs وqueue lag.
- اختبار smoke يدوي للصفحات الحرجة على سطح مكتب وهاتف.

### اختبارات قبول يدوية ثابتة

1. تسجيل الدخول والخروج وتبديل اللغة.
2. إنشاء/تعديل/حذف شركة وفرع وموظف حسب الصلاحية.
3. استقبال punch من جهاز معروف وغير معروف.
4. استقبال biodata وجه وبصمة ومعالجة duplicate.
5. فتح Dashboard وLive Attendance مع realtime.
6. تشغيل التقرير اليومي والشهري والتصدير.
7. إنشاء وتعديل rotation والـ assignment.
8. فتح Face Sync وإعادة محاولة أمر فاشل.
9. التأكد من أن مستخدم بلا صلاحية يرى 403 أو المنع المتوقع.
10. اختبار الهاتف، keyboard، focus، RTL وLTR.

## 9. ترتيب العمل العملي المقترح

### أول 3 أيام

- تثبيت baseline.
- تصنيف routes والمسارات الحرجة.
- مراجعة التعديلات المحلية القائمة.
- إضافة أو استكمال اختبارات الحماية للـ attendance/device/permissions.
- حفظ أول قياسات الأداء وحجم الحزمة.

### الأسبوع الأول

- إصلاح أعلى N+1 مثبتة فقط.

- مراجعة route/config cache في بيئة اختبار.
- إكمال الجداول والحقول في الصفحات الحرجة التي يمكن تحويلها بأمان إلى shared components.

## 11. تعريف النجاح النهائي

يُعتبر التطوير ناجحاً عندما:

- تبقى كل الوظائف الحالية تعمل بنفس العقود والنتائج.
- تصبح المسارات الحرجة محمية باختبارات آلية ومقارنات مخرجات.
- ينخفض زمن واستعلامات الصفحات الحرجة بناء على قياسات موثقة.
- تصبح الواجهة متناسقة على الصفحات الأكثر استخداماً دون نسخ مكونات جديدة.
- يعمل النظام بالعربية والإنجليزية، RTL وLTR، سطح مكتب وهاتف.
- يمكن اكتشاف فشل queue أو device sync أو slow request قبل أن يتحول إلى مشكلة تشغيلية.
- يمكن إيقاف أو عكس كل تغيير عالي الخطورة دون استعادة يدوية عشوائية.
- تكون كل مرحلة موثقة في specs أو docs مع دليل تحقق واضح.

## 12. الخلاصة التنفيذية

أفضل تطوير لهذا المشروع هو **تحسين محافظ مقاس ومجزأ**، وليس إعادة بناء. الأولوية الحقيقية هي حماية الحضور ومزامنة الأجهزة والتقارير، ثم بناء قياسات أداء ثابتة، ثم تحسين السرعة، ثم توحيد UI/UX على الصفحات الحرجة فوق المكونات الموجودة. أي خطة تتجاوز الاختبارات والمقارنة والرجوع قد تجعل المظهر أفضل لكنها تعرض الوظائف الأهم للخطر، لذلك تعتبر هذه البوابات جزءاً من التطوير نفسه وليست خطوة لاحقة.
